# E28 — end-to-end throughput and memory, W4A4KV4 vs fp16 (one A40)

**Setup.** One NVIDIA A40 (sm_86, `gpu-a40-1`, driver 580.173.02), no other process on the GPU (nvidia-smi logged before every run in `metrics_<row>.json`). QuaRot `spcl/QuaRot@5008669` (CUTLASS 3.4.1 INT4 GEMM, `sym_quant`/`sym_dequant`, FlashInfer INT4 paged KV cache, fast-hadamard-transform 1.0.4.post1), built with nvcc 12.4 into torch 2.4.1+cu124 / triton 3.0.0 / transformers 4.36.2 / flash-attn 2.6.3; the E17 v3 microbenchmark ran in the main environment (torch 2.11.0+cu128, triton 3.6.0). Random INT4 weights and random fp16 weights (QuaRot's benchmark convention; seed 0). Prefill 2048 tokens at batch 1 and 16; decode batch 1, 128 tokens after a 2048-token prefill, tokens 9–128 averaged; every measurement `torch.cuda.synchronize`d, 10 warmup, **median ± std over 50 runs**. Peak memory is `max_memory_allocated` during the batch-16 prefill and during decode, reported separately in `results/e28/{3b,8b}/metrics.json`; the table shows decode.

**Reading the table.** *Prefill:* QuaRot's INT4 pipeline is 1.25×/1.29× (3B) and 1.44×/1.50× (8B) faster than fp16 at bs 1/16; PrismQuant retains 86 %/94 % of that speedup on the 3B and 103 %/103 % on the 8B (the transform sits inside the down_proj slot and costs 0.18 vs 0.11 ms per layer at 2048 tokens on the 3B, 0.29 vs 0.20 ms on the 8B, see `nar_kernel_selection.json`). *Decode at batch 1 is slower than fp16 for both INT4 rows.* This is a property of QuaRot's released pipeline, not of the transform: the profiler puts the GPU kernel time per decode step at 17.0 / 18.7 / 19.1 ms (3B fp16 / Hadamard / PrismQuant) and 30.9 / 25.9 / 26.5 ms (8B) against wall-clock 42 / 70 / 70 and 53 / 82 / 79 ms, with 2.5k–4.2k kernel launches per token; the INT4 path issues ~1.4× more launches (quantizers, online Hadamards, KV scale handling) and is CPU-launch-bound. So the "% of Hadamard speedup" for decode compares two slowdowns; the row-3 minus row-2 decode difference is what the slot costs: **+0.42 ms/token on the 3B (0.6 %) and −2.98 ms/token on the 8B** (PrismQuant's two pre-bound Triton launches replace QuaRot's K=28 Hadamard path of view + FHT + `had_28` matmul + dtype copy, which has more Python per layer). The GPU-time diagnostic in the same JSON shows the kernels themselves: +0.38 ms (3B) and +0.59 ms (8B) per token for PrismQuant. *Memory:* row 3 equals row 2 plus **23.2 MB (3B) and 45.2 MB (8B)** in both phases, of which the factors are 22.0 / 44.0 MB (768 KB / 1.34 MB per layer, not the ~256 KB of the spec: Y' is carried as two fp16 hi/lo terms zero-padded to 16 ranks for `tl.dot` (64 N bytes) and W'' as fp16 hi/lo (32 N bytes); the 1.2 MB remainder is one shared fp32 partial buffer plus the shared 32 KB H₁₂₈). The GPU also holds `Linear4bit.weight_scales` and the KV scales, identical across rows 2 and 3.

**Every modification to QuaRot** (full list with rationale in `quarot-llama3/README.md`): (1) GQA in the FlashInfer decode kernel — Llama-3 has 8 KV heads for 24/32 query heads; query head h reads KV head h/(H_q/H_kv), wrappers launch per query head (`quarot_gqa_decode.patch`, the only source change). (2) `build_cache` head dimension: `hidden/num_kv_heads` (=512 for Llama-3) → `hidden/num_heads` (=128). (3) Llama-3 RoPE: transformers 4.36 rejects `rope_type: llama3`; the config is loaded without it and the ≥ 4.43 inverse frequencies are installed on every layer. (4) R2 online Hadamard for 24 heads (3B only): QuaRot's path factors 24 = 12×2 into a length-2 FHT plus 3M tiny `had_12` matmuls (2.2 ms/layer, 30 % of prefill); replaced by the identical H₂₄ as one 24×24 fp16 GEMM, checked against QuaRot's function at construction, used by rows 2 and 3 alike. (5) Prefill logits computed for the last position only (all rows): full 128 256-vocab logits upcast to fp32 are 25 GB at bs 16 and do not fit next to the 8B fp16 weights. (6) Environment: QuaRot's last commit bumps its transformers pin to 4.38.0, under which its e2e model does not run (`from_legacy_cache` on its custom cache, changed rotary signature); the e2e-era 4.36.2 is used. (7) Random weights are made finite explicitly (`no_init_weights` leaves fp16 parameters uninitialised, `weight_scales` zero) and `tie_weights()` is called for the 3B's tied LM head.

**Deviations from the spec.** *fp16 instead of bf16 for row 1:* QuaRot's fp16 KV-cache kernels are half-precision only; A40 tensor-core throughput is identical for the two. *The E17 v3 kernel was adapted for sm_86 and for QuaRot's quantizer* (allowed by the "kernel may be optimised" instruction): Kernel A (`rank_projection_dot_kernel`) is unchanged; Kernel B keeps E17's structure but runs the block-Hadamard-128 as a `tl.dot` with a ±1 fp16 H₁₂₈ and the rank-k correction as three fp16 hi/lo `tl.dot`s (E17's shuffle FWHT runs at 2.4× the copy floor on the A40; the tensor-core version is within 8 % of it), and stores fp16 instead of E17's group-128 asymmetric INT4 because QuaRot's GEMM consumes per-token symmetric INT4 from QuaRot's own `Quantizer`, which is kept byte-identical in rows 2 and 3. Every config was verified against the fp32 reference before timing (31/31 pass; worst-layer code match after QuaRot's quantizer 0.99969 vs 0.99971/0.99956 for QuaRot's own fp16 Hadamard on the 3B/8B), and the kernels are launched through Triton's pre-bound `CompiledKernel` runner (checked bit-for-bit) because decode is launch-bound. *Correctness pass not run:* per the user's instruction ("只要测速度吞吐量内存，不要测试完整benchmark"); it would also not be a like-for-like test, since QuaRot's integer path quantises activations per token symmetric and the KV cache per head asymmetric with a Hadamard on K, whereas the paper's fake-quant rows use group-128 asymmetric activations and KIVI. *One placeholder allocation* (`sbatch --gpus=a40:1`, 4 CPUs, 40 GB host RAM) hosted all runs via `srun --overlap`; the SLURM enforced CPU count is what makes the launch-bound decode numbers what they are.

**E17 v3 kernel on the A40** (`nar/e17_v3.py` unchanged, k = 8, `results/e28/e17v3_a40_summary.json`; 100 (shape, config) combinations tested per model, 43/25 verified): at 2048 tokens NAR/Hadamard is **1.61× (3B, 0.264 vs 0.164 ms) and 1.59× (8B, 0.445 vs 0.281 ms)** against 1.80×/1.48× on the RTX PRO 6000 in E17; at 1 token 2.88×/3.16×, at 32 tokens 2.21×/2.53×. Achieved bandwidth at 2048 tokens by E17's byte model: Hadamard 259 / 265 GB/s, NAR 416 / 299 GB/s (traffic ratio 2.58 with the 2-term cuBLAS Kernel A on the 3B, 1.79 with the Triton Kernel A on the 8B) — both far below the A40's 696 GB/s, because E17's shuffle-based Kernel B is compute-bound on sm_86 (the reason the E28 row-3 kernel uses tensor cores). The E17 gate (≤ 2.0× at 2048 tokens) passes on both models.
